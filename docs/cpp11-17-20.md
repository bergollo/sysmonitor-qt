# C++11, C++17, and C++20

This project started from a C++11-era foundation and now builds as C++20.
The goal is not to memorize every standard-library addition. The useful
senior-level skill is recognizing which language feature makes ownership,
constraints, failure, or data flow clearer.

## Timeline

| Standard | Main shift | Project relevance |
|---|---|---|
| C++11 | Modern ownership, lambdas, move semantics, concurrency vocabulary | The baseline assumed by this refresher |
| C++14 | Smaller usability improvements to C++11 | Generic lambdas and relaxed `constexpr` |
| C++17 | Safer value types and practical library additions | `std::optional`, `std::filesystem`, structured bindings |
| C++20 | Expressive constraints, views, compile-time tools, and ranges | The project language level; selected features are introduced deliberately |

## C++11 Baseline

The C++11 features most relevant here are `auto`, range-based `for`, lambdas,
`nullptr`, `enum class`, `constexpr`, `static_assert`, smart pointers, move
semantics, `std::thread`, and `std::chrono`.

The Qt worker deliberately uses `QThread` instead of `std::thread` because the
worker needs a Qt event loop for `QTimer` and queued signals. C++20 does not
make a standard thread automatically interchangeable with a Qt thread.

## C++14 Bridge

C++14 made generic lambdas, lambda capture initializers, return type deduction,
and relaxed `constexpr` practical. These features reduced ceremony, but many
teams moved from C++11 directly to C++17, so they are useful historical context
rather than a separate project target.

## C++17 Features Used Here

### `std::optional`

Parser failures are represented explicitly instead of using sentinel values:

```cpp
[[nodiscard]] std::optional<MemoryInfo> readMemoryInfo();
```

### `std::filesystem`

Thermal-zone discovery uses standard path and directory types. This is safer
than manually concatenating strings and makes the platform boundary clearer.

### Structured Bindings and `if constexpr`

These are important C++17 tools, even where this small project does not need
them yet. Structured bindings unpack tuple-like values; `if constexpr` removes
invalid branches during template instantiation.

### Other Useful C++17 Additions

- `std::variant` models a closed set of alternatives.
- `std::string_view` provides a non-owning string view.
- Fold expressions simplify variadic templates.
- `[[nodiscard]]` asks the compiler to warn when a meaningful result is ignored.
- Class template argument deduction reduces repetitive template arguments.

## C++20 Features

### Concepts

Concepts express template requirements directly:

```cpp
template <typename T>
concept Numeric = std::is_arithmetic_v<T>;
```

They are preferable to complex SFINAE when a genuinely generic API needs
constraints. This project should not add a generic abstraction merely to show
the syntax.

### Ranges

Ranges compose algorithms and views without manually managing iterator pairs.
They are useful for collection transformations, but filesystem iteration with
side effects should remain straightforward unless a range makes the code more
readable.

### `std::span`

`std::span<const T>` is a non-owning view over contiguous data. It is useful
when a helper should accept either a `std::vector`, an array, or a subrange
without taking ownership. A span must never outlive the storage it references.

### Designated Initialization

C++20 permits named aggregate members:

```cpp
const CpuTimes snapshot{
    .user = 100,
    .system = 50,
    .idle = 850,
};
```

The tests use this for readable fixtures. It is especially valuable when a
struct has many fields and only a few are relevant to the test.

### Defaulted Comparisons

`CpuTimes::operator==` is defaulted in C++20. The compiler compares each data
member, which makes value-object tests concise without hand-writing equality
code.

### `consteval`, `constinit`, and Better `constexpr`

`consteval` requires compile-time evaluation; `constinit` requires static
initialization; C++20 also makes more standard-library operations usable during
constant evaluation. These are useful for configuration invariants, but should
not obscure ordinary runtime code.

### `std::jthread` and Stop Tokens

`std::jthread` provides joining and cooperative cancellation. It is not a
drop-in replacement for this project's `QThread`: the worker relies on Qt's
event loop, `QTimer`, and queued signal delivery. Compare the two models before
changing the architecture.

### Coroutines, Modules, and `std::format`

These are important C++20 features but remain intentionally out of the core
implementation:

- Coroutines are unnecessary for a one-second event-driven poll.
- Modules add build/tooling complexity around Qt MOC and resource generation.
- `std::format` is not needed while presentation uses `QString` and may add
  standard-library portability concerns across target images.

## Migration Rules

Do not modernize mechanically. Prefer a C++20 feature when it improves an API,
documents an invariant, or removes a real source of error. Keep Qt facilities
where they define the application boundary, and keep standard C++ in the core
where display-free tests and platform substitution matter.
